Operating playbook

Lessons learned

Initial lessons inherited from HMSA plus CSR-specific findings added as the run progresses.

1. Profile once, execute from bundles

  • Opus profiles the complete source corpus programmatically.
  • P0 reduced 100 source files to five queryable profile tables plus one durable source_profile.json attachment before compiling stage contracts.
  • Later stages consume one compiled bundle rather than rereading all 100 plans.
  • Source documents remain reference-only and never become conversation payload.
  • Do not SELECT a large assignments or schema object through the chat-facing query tool; run a project script that parses the bundle and writes shard files directly, returning only filenames, hashes, and validation summaries.
  • Once prerequisites and ownership are known, stop discovery. Repeatedly extracting contract sections is not execution and should trigger an early stop plus compact handoff.
  • A compact file can still be context-heavy if stored as one long line and read through chat. Make handoffs pretty-printed and range-readable, forbid chat file_read, and require direct script parsing with bounded summaries.

2. Budget turns and context separately

  • Use the extended 120k/130k/145k policy with 60k and 110k handoffs.
  • Use enough turns for generation, validation, and checkpointing.
  • Persist useful work before either budget becomes tight.
  • Do not equate conversation-scoped usage with one model context: P0 reached 624,550 aggregate tokens largely through cached and repeated input while the turn remained active.
  • Measure compiled bundles, not just source inputs: embedding full schema statistics pushed estimated bundle size to about 78k tokens, already above the 60k rolling-handoff threshold.
  • E1's initial 12-turn cap expired entirely in discovery and preflight. Execution stages need a turn budget that covers bundle verification, generation, validation, repair, and checkpoint writing—not merely startup.
  • Complex shard adaptation should be split into discovery and bounded edit passes. E1 shard 3 reached 111,713 direct-input tokens while recovering missing schema shapes, so stopping before a large script write preserved a clean continuation boundary.
  • Even an edit-only pass can consume its turn budget while refining schema-coherent conditional groups. Budget a separate, tiny type-check/inspection continuation instead of squeezing verification after the final replacement.
  • Large whole-file Opus reviews can consume millions of cached and ephemeral tokens while the visible turn is stationary. Treat review as its own budgeted stage, and reserve turns for the resulting fixes plus final type-check and re-review.
  • Turn budgets can expire well below the direct-context ceiling: I4 stopped after metadata discovery at 57,899 ephemeral-input tokens. Once required schema paths are known, minimize query count and spend the next bounded turn authoring one persisted validator.
  • The I4 continuation rose from 70,063 to 170,520 direct ephemeral-input tokens while checking and executing one validator, exceeding the 145k hard-stop target. Native check and execution output can add substantial context; reserve margin before both steps or rotate first.

3. Make continuation deterministic

  • Preallocate plan IDs, nested namespaces, and filenames.
  • On resume, accept hash-matched passing files and continue at the incomplete shard.
  • Never replay P0 or regenerate a passing plan to rebuild context.
  • An in-place retry cannot recover if the platform fails while summarizing the existing conversation; a separate continuation can instead reuse durable project artifacts without replaying profiling.
  • A cooperatively stopped conversation can resume through a follow-up turn without creating another conversation or duplicating its project databases.
  • A compact continuation can verify the exact saved script by filename and character count, then run one scoped validator without importing the prior transcript or source corpus.
  • Validator review caught random UUID generation and per-plan phone synthesis; seeded identifiers and shared fictional servicing-team lines improve both reproducibility and realism.

4. Scope validators tightly

  • Require findings to cite the current stage contract and exact JSON paths.
  • Defer out-of-scope findings rather than broadening repairs.
  • Separate approved legacy schema keys from prohibited value/content scans.
  • Validate cross-field semantics, not just types: the second pass caught over-allocated pharmacy carve-outs and an incompatible first-dollar/no-deductible flag combination.
  • After a large repair batch, complete type checking before launching another validator; parallel review wastes validator context when the saved script does not parse.
  • Give generated arrays explicit element types before review and execution; E1 shard 1 otherwise lost context to TS18046 because cat was inferred as unknown.
  • The deidentification contract allows no VALUE_PASS exemptions. If a generated display label contains a prohibited token, neutralize that synthetic label while preserving its nexus/category IDs and internal name consistency.
  • Template-content rules should be proven across every variant before execution; one category prose variant omitted the literal limit token expected by CNT-01.
  • Reusable generators need shard-specific semantic preflight, not only literal replacement checks. Shard 2 inherited a COH-03 assertion that rejected all HDHP assignments even though its variation matrix intentionally includes one.
  • For planned HDHP records, COH-03 must validate the bundled design thresholds—not assert !a.hdhp: PSP or EPO Savings, hsaQualified, deductible at least 1,700/3,400, OOPM at most 8,750/17,500, and no separate pharmacy deductible. C7100005's 3,300/6,600 and 6,600/13,200 values satisfy them.
  • Generation and validation predicates must use the same evidence scope. Shard 3 selected the member-maximum target from category, subcategory, or benefit text, but COH-15 initially rechecked only the benefit name.
  • A planned conditional group must be emitted at the exact contracted hierarchy. Member-maximum fields belong on provider cost shares, not benefits; type safety cannot catch a structurally valid object at the wrong path.
  • When repeated bulk edits deeply corrupt generated code, a clean single rewrite can be safer and smaller than attempting surgical deletion; type-check the saved source before renewed validation.
  • Every database row set that feeds a serialized, hashed artifact needs an explicit stable ordering; storage-engine iteration order is not a reproducibility contract.
  • With SQLite JSON1, iterate object keys directly from json_each; applying json_type() to scalar text values can raise a misleading malformed-JSON error.
  • Type checks and code review do not prove runtime compatibility. Before an execution-only shard, exercise environment-sensitive self-read logic and validate the exact shard-delta key set in a non-writing gate.
  • Use Fabricate's native saved-script type checker. A custom helper that shells through Deno.execPath can fail because that API is unavailable even when the generator itself is valid.
  • A numeric target formula must be bounded by the selected catalog's actual capacity. E2 passed type checking but S7200003 could not supply the requested subcategory count from its chosen categories.
  • Contradictory evidence such as “flagged empty” alongside a nonzero observed array length indicates validator instrumentation failure, not a data defect. Mark the output superseded explicitly and never use it as repair authority.
  • Contract-aware final validation must use flags.includes, treat only OOP Maximum as a universal EOC section, avoid coupling pharmacy metadata to a nested Pharmacy plan, exclude keys from VALUE_PASS, and accept E1 immutable_plan_manifest as a valid completion source.
  • Canonicalization tests must use the contract's actual NUL separator, not the two-character text \0, and validators must not promote source-profile observations into gates unless the contract does.

5. Verify durable outputs

  • A successful tool event is not proof that a file persisted.
  • Reconcile filename, identifier, hash, parse status, and stage ownership.
  • Checkpoint gates—not UI state—determine completion.
  • P0 proved that durable profile outputs can survive a failed turn, but those partial artifacts do not prove that downstream contracts or bundles were completed.
  • The cooperative pause landed after file-write and validator calls completed, yet no downloadable continuation file or populated build table exists; a safe process boundary is not automatically a durable handoff.
  • A failed gate must abort before emitting downstream artifacts; a checkpoint must never claim completion or zero unresolved issues when any gate check fails.
  • Verify replacement anchors are unique: bulk edits accidentally inserted two complete script copies inside a Markdown template, tripling file size and breaking parsing.
  • Fabricate's completed/awaiting_user state can coexist with a stopped validator. Treat it as a handoff, not stage completion, unless durable gate and checkpoint artifacts exist.
  • One scoped validator, one consolidated edit, one type check, and one execution produced a clean 16/16 gate; reconcile the resulting database inventory independently before declaring the stage complete.
  • Run the compact filename/hash/checkpoint reconciliation immediately after a successful write. E1 shard 1 hit the turn cap after loading verification helpers, but independent database reconciliation still proved its five durable rows.
  • Close or rotate immediately after durable gate verification. A post-success response failure does not justify rebuilding already verified artifacts; preserve the failure in the audit trail and continue from the checkpoint.
  • Verification queries must respect artifact content type. Applying JSON extraction to a Markdown handoff creates a false malformed-JSON error; use metadata hashes or content-type-aware parsing.
  • Do not expand a no-execution preparation script merely to obtain its own digest. Compute the hash in a tool that can read persisted bytes, or pin it at the start of the authorized execution stage.
  • Listing database tables proves only schema availability. A shard preflight that depends on checkpoint or receipt state must query the exact bounded row names before deciding whether execution is safe.
  • When an integration gate fails, persist only the bounded defect ledger and withhold PASS artifacts. Adjudicate universal or accounting-shaped findings against the stage contract before treating them as data defects.
  • Final validation must distinguish process-artifact gaps from validator drift. V6 found one genuine missing checkpoint, while five other findings arose from checkpoint-count, universal-section, or allowlist assumptions that did not match the approved data contract.
  • A targeted plan repair must update both the source record and package copy, then rebuild the manifest, canonical checkpoint hash, and ZIP from stable bytes. Two independent ZIP rebuilds should be byte-identical before external persistence.

6. Track cost where it occurs

  • Record every conversation, including retries and repair sessions.
  • Include subagent and validator usage in conversation totals.
  • Roll costs up by stage so expensive loops remain visible.
  • Treat a lone monitoring transport error as inconclusive; the next scheduled poll can distinguish API turbulence from an actual run failure.
  • Metadata-only reconciliation must select metadata columns only. Selecting full plan content to report hashes inflated the E3-sub1 retry by more than two million tokens after the durable gate had already passed.
  • Final validation must honor per-record modifiers: F7300002's AIAN condition is record-specific, pharmacy metadata is independent of a nested Pharmacy plan, and E1's immutable manifest can legitimately document the three tracked repairs.
